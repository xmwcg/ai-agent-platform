## 2. 评分方法

ProjectGrade Batch 0 使用确定性评分，不允许 LLM 直接决定最终分数。

```text
规则得分 = 规则权重 × 完成度 × Evidence 系数
维度得分 = 该维度下所有规则得分之和
原始总分 = 12 个维度得分之和
最终总分 = min(原始总分, 最高严重性门禁分数上限)
外显分 = 最终总分 ÷ 10
```

完成度只允许：`0 / 0.25 / 0.5 / 0.75 / 1`。

Evidence 系数：

| Evidence 等级 | 系数 | 含义 |
|---|---:|---|
| `production_automatic` | 1.00 | 与本次运行绑定的生产自动验证；只有带 `verifiedAt` 的证据才可推动生产验证状态 |
| `ci_integration` | 0.90 | CI、集成或端到端自动化证据 |
| `source_static` | 0.75 | 源码、配置和静态实现线索 |
| `documentation` | 0.40 | 文档声明或计划 |
| `none` | 0.00 | 无证据 |

门禁封顶：P0 最高 390/1000，P1 最高 590/1000，P2 最高 690/1000，P3 最高 790/1000。门禁不会额外加分，只会限制最高可得分。

## 6. Findings 与整改建议

### P1 — 核心用户旅程缺少本次生产自动验证

- **问题**：当前只有源码线索，无法证明登录、AI、保存、分享、下载和异常恢复在生产真实可用。
- **整改**：建立 Playwright 生产只读探针，保存请求、响应、截图、控制台和失败证据；探针必须与具体 revision 和运行 ID 绑定。

### P1 — AI 核心能力缺少版本化测试集和生产证据

- **问题**：尚未用固定测试集验证真实模型回复、引用、幻觉、Prompt 注入、延迟和成本。
- **整改**：建立版本化基准测试集、多模型运行记录和生产调用追踪；Mock 结果不得计入生产 Evidence。

### P1 — 支付、权益与交付闭环未在本次运行中验证

- **问题**：源码存在不能证明支付验签、幂等发权、退款、下载或 License 在真实环境工作。
- **整改**：完成微信支付沙箱/生产验签、订单幂等、权益到账、退款和交付的端到端验证，并保存订单、回调、账本和交付证据。

### P1 — 正式发布四端版本一致性未验证

- **问题**：本轮没有 CNB `main`、`deploy/production`、GitHub 镜像和服务器镜像 revision 的一致性证据。
- **整改**：在 CNB 正式链路成功后核验四端 revision、健康探针和回滚路径；CNB 仍是唯一正式发布源。

### P2 — 服务端严格类型检查尚未开启

- **问题**：`server/tsconfig.json` 当前 `strict=false`，降低重构和规则引擎演进的类型安全。
- **整改**：建立 ProjectGrade 严格子配置，分模块收敛 `any`、隐式类型和可空边界，再评估全局开启 strict。

### P2 — 移动端和无障碍证据缺失

- **问题**：未发现与本次运行绑定的手机、键盘、对比度和 axe/Lighthouse 结果。
- **整改**：为 ProjectGrade 和核心购买路径增加响应式、键盘、焦点、对比度和 axe/Lighthouse 自动检查。

### P3 — 性能、容量和 AI 成本基线缺失

- **问题**：当前没有目标并发、P95 延迟、队列容量和单次评估成本证据。
- **整改**：定义 SLO，执行负载测试并记录容量、失败率、队列积压和成本预算；为超预算和超时建立告警。

### P3 — 规则版本、整改 SLA 和复测趋势尚未形成闭环

- **问题**：已有文档和客服源码，但缺少 ProjectGrade 规则治理、负责人、截止时间和提分趋势。
- **整改**：建立规则版本、整改任务、负责人、SLA、状态流转、复测关联和分数趋势报告。
